# ADR 017: 비정형 데이터셋 식별자 — URN 규칙과 external_ids

> **Date:** 2026-10-29
> **Status:** Accepted
> **Related:** ADR-014 (스키마 정본 소유권)

---

## 배경

협력기관과 `dataset_id`를 URN 형식으로 통일하기로 합의했다. 정형은 원천 포털의
고유번호를 그대로 쓰면 되지만, **비정형에는 그런 번호가 없다.**

기존 비정형 `dataset_id`는 `samsung_official`, `news_ai` 같은 slug였다.
전환 범위·절차·실행 기록은 database/dataset_id_urn_migration.md에
있고, 이 ADR은 **규칙 자체와 그렇게 정한 이유**를 남긴다.

> 전환은 정형 데이터 적재 **전에** 완료했다. 적재 후였다면 FK `ALTER`가
> 양측 합의 사항이 되고 전환 범위에 상대 데이터가 들어갔을 것이다.

## 결정

### 1. 형식

```
urn:{네임스페이스}:{수집단위키}

정규식: ^urn:[a-z0-9]+:[a-z0-9_]+$
상한  : 100자
```

- 네임스페이스는 **원천의 소문자 영문 약칭** (`naver`, `youtube`)
- **네임스페이스에 `_`를 쓰지 않는다** — §3의 역변환을 보장하기 위한 제약이다
- 수집단위키에는 `_` 허용

### 2. 원천이 아니라 '수집 단위'를 키로 쓴다

```
urn:naver:news_ai            (원천 naver / 수집 단위 '뉴스·AI 검색어')
urn:youtube:samsung_official (원천 youtube / 수집 단위 '삼성 공식 채널')
```

**비정형 데이터셋은 원천 객체와 1:1로 대응하지 않는다.** 같은 YouTube 채널로
기간·필터가 다른 데이터셋을 둘 만들 수 있어, 채널 ID를 식별자로 쓰면 충돌한다.
그래서 식별자 자리에는 수집 단위 키를 넣고, **원천 객체 키는 `external_ids`에
보존한다** (2026-10-28 협력기관 승인).

`origin`(admin/user)은 식별자에 넣지 않는다. `dataset_origin` 컬럼이 이미
구분하고 있어 중복이고, 등록 주체가 바뀌면 식별자까지 흔들린다.

### 3. S3 경로는 `storage_key()`로 변환한다

```python
urn:naver:news_ai            → naver_news_ai
urn:youtube:samsung_official → youtube_samsung_official
```

`urn:` 접두를 떼고 나머지 `:`를 `_`로 바꾼다. 콜론은 S3 키에 쓸 수는 있지만
URL 인코딩·CLI 인용·일부 도구에서 걸린다.

**이 변환 결과가 전환 전 slug와 같다.** 따라서 URN 전환 후에도 기존 S3 경로가
그대로 유지된다(실측: 객체가 있는 경로 6개 전부 보존). S3에는 rename이 없어
경로 이전은 복사 후 삭제가 필요한데, **경로가 식별자와 일치해야 할 이유가 없어
그 비용을 치르지 않기로 했다.**

> ⚠️ 네임스페이스에 `_`가 있으면 이 변환을 되돌릴 수 없다(`a_b_c`가
> `a_b`+`c`인지 `a`+`b_c`인지 알 수 없다). §1의 제약은 이 때문이다.

### 4. 채번 — 제목에서 키를 만들지 않는다

```
urn:naver:news_dataset_a3f1c2     (secrets.token_hex(3), 충돌 시 5회 재시도)
urn:youtube:dataset_5c81af
```

이전에는 `slugify(title)`을 썼는데 **결과를 예측할 수 없었다.**

| 제목 | slug 결과 |
|---|---|
| `AI 관련 뉴스` | `ai` (AI만 살아남음) |
| `인공지능 뉴스` | `dataset` (남는 게 없음) |
| `반도체 HBM` | `hbm` |

한글 제목은 거의 다 `dataset`으로 떨어져 의미가 없었고, 영문 제목은 제목을
조금만 바꿔도 식별자 모양이 달라졌다. **의미는 `title` 컬럼이 들고 있으면 되고,
식별자는 유일하고 안정적이기만 하면 된다.**

읽을 수 있는 키가 필요하면 `--dataset-id`로 직접 지정한다(형식 검증은 동일 적용).

### 5. `external_ids` — 원천 객체 키 보존

협력기관 정의는 `adms:identifier`, 형식은 `"네임스페이스:값"` 문자열 배열이다.
같은 데이터셋이 다른 경로로 두 번 수집될 때 중복을 탐지하는 컬럼이다.

**video** — 채널 ID. 원천이 발급한 진짜 객체 키다.
```
["youtube:UCWwgaK7x0_FR1goeSRazfsQ"]
```
개별 영상 ID는 넣지 않는다. 영상은 데이터셋의 원천 객체가 아니라 그 안의
항목이고 `meta_video`가 이미 들고 있다.

**그 외** — 수집 조건 **집합**의 해시.
```
["naver:news:sha256-3c639c929baf"]
```

개별 검색어를 그대로 넣으면 **조건 하나만 겹쳐도 중복으로 오판**한다 —
실제로 `shopping_insight`와 `shopping_insight_advertiser`는 카테고리
`50000148`을 공유한다. 집합 전체를 해시하면 완전히 같을 때만 겹친다.

### 6. 집합 해시 규약

```
정규화: 공백 제거 → 소문자 → 중복 제거 → 코드포인트 정렬 → '|' 결합
해시  : sha256 앞 12자, 'sha256-' 접두

['인공지능','AI','머신러닝','딥러닝'] → 'ai|딥러닝|머신러닝|인공지능'
                                    → 'sha256-3c639c929baf'
```

**정렬 덕분에 검색어를 적은 순서는 영향이 없다.** 원문은 `subjects` 컬럼에
그대로 남아 해시는 언제든 재생성할 수 있다.

세 가지 선택에 각각 이유가 있다.

| 선택 | 이유 |
|---|---|
| sha1이 아니라 **sha256** | PostgreSQL에 `sha256()`이 내장돼 있어 SQL에서도 같은 값을 만들 수 있다. `sha1()`은 내장이 아니다 |
| **`sha256-` 접두** | `adms:identifier`는 "원천이 발급한 고유번호"인데 이 해시는 **어떤 기관도 발급한 적 없는 합성값**이다. 접두가 없으면 `naver:news:3c639c929baf`가 네이버 발급 ID처럼 보인다 |
| 앞 **12자** | 충돌 확률과 가독성의 절충. 원문이 `subjects`에 남아 있어 충돌 시 판별 가능 |

> ⚠️ **SQL에서 같은 해시를 만들려면 `COLLATE "C"`가 필수다.**
> DB 기본 콜레이션은 한글을 영문보다 앞에 두어 Python `sorted()`와 결과가 다르다.
> ```
> SQL 기본      : 딥러닝|머신러닝|인공지능|ai
> SQL COLLATE C : ai|딥러닝|머신러닝|인공지능   ← 파이썬과 일치
> ```

## 받아들이는 대가

- 식별자만 보고 데이터셋 내용을 알 수 없다(`urn:naver:news_dataset_a3f1c2`).
  `title`을 함께 조회해야 한다 — 식별자의 안정성과 맞바꾼 것이다.
- `external_ids` 집합 해시는 **사람이 읽을 수 없다.** `subjects` 원문을 함께 봐야 한다.
- 네임스페이스에 `_` 금지 제약이 원천 약칭 선택을 제한한다
  (예: `naver_news`가 아니라 `naver` + 수집단위키 `news_*`).
