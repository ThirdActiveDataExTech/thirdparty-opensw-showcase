# ADR 010: 한국어 전문검색 — 애플리케이션 단 토큰화 + simple tsvector

> **Date:** 2026-10-27
> **Status:** Accepted

---

## 배경

현재 검색은 pgvector 코사인(벡터) **단일 채널**이다. 하이브리드 검색을 구성하려면
키워드 채널이 필요한데, **PostgreSQL 기본 FTS는 한국어 형태소 분석을 지원하지 않는다.**

## 선택지

| 후보 | 판정 | 사유 |
|---|---|---|
| **앱단 형태소 토큰화 → `simple` tsvector + GIN** | **채택** | 아래 |
| `pg_trgm` | **보조 채널로만** | 3-gram. 한글 2글자 이하 질의는 인덱스 미사용. 조사 결합·어미 변화에 취약. `similarity()`는 의미적 랭킹이 아님 |
| `pg_bigm` | 탈락 | 소스 빌드 → **이미지 재빌드 + `shared_preload_libraries` 변경 + 재기동** 필요. **LIKE 연산자 전용**이라 하이브리드 결합에 쓸 점수가 `bigm_similarity` 하나뿐 |
| `PGroonga` | 탈락 | 동일한 이미지 재빌드 비용. 형태소 토크나이저 기본 사전이 일본어용이라 **한국어 품질 이점이 불확실**. 과거 문서의 크래시 세이프 이슈 |
| OpenSearch + Nori | 탈락 | [ADR-003](003_VectorDB_Strategy.md) 기조와 동일. 상시 클러스터 1식 + PG↔ES 동기화(이중 진실원천) |

## 결정

**Kiwi(앱단)로 토큰화한 결과를 `simple` 설정 tsvector에 넣고 GIN 인덱스를 건다.**

근거:

1. **DB 확장 설치가 불필요하다** — 컨테이너 이미지 재빌드·설정 변경·재기동이 전부 사라진다.
   pg_bigm·PGroonga는 모두 이것이 전제다.
2. `ts_rank_cd` 랭킹과 `tsquery`의 AND/OR/구문검색을 그대로 쓸 수 있다.
3. 이 규모에서 선택 기준은 속도가 아니라 **운영 리스크와 랭킹 품질**이며, 두 축 모두 유리하다.
4. 형태소 분석기를 교체해도 **DB 스키마는 불변, 재색인만** 하면 된다.
5. 질의·문서에 **동일 토크나이저**를 쓰므로 "조사가 분리되지 않는다"는 한국어 고질 문제가
   설계 단계에서 제거된다. n-gram 계열은 이를 확률적으로 우회할 뿐이다.

### 구현 시 반드시 지킬 것

> `array_to_tsvector(tokens)`를 쓰면 **위치 정보가 없어 `ts_rank`/`ts_rank_cd`를 쓸 수 없고
> 소문자 정규화도 되지 않는다.**
> 반드시 `to_tsvector('simple', array_to_string(tokens, ' '))` 형태로 생성한다.

- 필드 가중치는 `setweight`로 제목 A / 키워드 B / 설명 C.
- `tokenizer_ver` 컬럼을 두고 **기동 시 버전 일치를 검증**한다.
  질의·문서 분석기가 불일치하면 **조용히 리콜이 0**이 되므로, 불일치 시 기동 실패시킨다.
- `to_tsquery`에 사용자 입력을 직접 넣지 않는다. **토큰 화이트리스트 기반으로 조립**한다.

### 결합: RRF

벡터 채널과 키워드 채널은 **Reciprocal Rank Fusion**으로 결합하고, **SQL 단일 CTE**로 구현한다.
점수 정규화 가중합은 채널별 분포 통계가 필요한데 현 규모에서는 통계가 신뢰할 수 없다.
`k`는 통상 60이 기본값이나 후보군이 작아 과도하게 평탄화될 수 있으므로
`k ∈ {10,20,30,60}` 스윕을 평가 항목에 포함한다.

## 형태소 분석기

**Kiwi (`kiwipiepy`)** 를 사용한다. ⚠️ **0.24.0부터 Apache-2.0, 0.23.2 이하는 LGPL — 버전 고정 필수.**
모델 파일을 패키지에 동봉하므로 런타임 외부 다운로드가 없어 폐쇄망에 유리하다.
