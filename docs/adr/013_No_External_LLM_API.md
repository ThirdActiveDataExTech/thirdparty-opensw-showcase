# ADR 013: 외부 LLM API 미사용 — 로컬 추론 전용

> **Date:** 2026-10-27
> **Status:** Accepted

---

## 배경

AI 생성 메타데이터(A2), 질의 확장(C2), 검색 품질 평가(C1)의 설계는
**외부 LLM API를 호출할 수 있는지**에 따라 갈린다. 2026-10-27 확인 결과
**외부 LLM API 사용은 어렵다**는 판단이 내려졌다.

추가 제약: 서버에 **GPU가 없다**(infrastructure/01_Current_Infrastructure.md).

## 결정

**모든 언어모델 추론을 온프레미스 로컬로 한정한다. 외부 LLM API에 의존하는 기능은
그것 없이도 동작하도록 설계한다.**

핵심 원칙: **LLM이 없어도 기능이 성립해야 하고, LLM은 품질을 올리는 선택지여야 한다.**

## 기능별 대체 경로

### A2. AI 생성 메타데이터

| 단계 | 방식 | LLM 필요 |
|---|---|---|
| 🟩 **최소선** | **추출 요약**(문장 중요도 기반 선택) + TF-IDF 키워드 + Kiwi NNP·gazetteer 개체명 | **불필요** |
| 🟦 목표선 | 로컬 sLLM 생성 요약 (llama.cpp + Qwen3 4B급 Q4, **Apache-2.0**) | 로컬만 |

최소선을 **완전히 LLM 없이** 구성한다. 추출 요약은 생성 요약보다 품질은 낮지만
**원문에 없는 내용을 만들어내지 않아(hallucination 없음) 메타데이터 용도에는 오히려 안전하다.**
B1에서 확정한 Kiwi 파이프라인을 그대로 재사용하므로 추가 의존성이 거의 없다.

### C2. 질의 확장

LLM 기반 확장어 생성 대신 **카탈로그 전체에서 공기어(co-occurrence) 테이블을 미리 만들어
상위 N개를 추가**한다. 완전 오프라인이며 구현은 반나절 수준이다.
확장어는 **키워드 채널에만** OR로 추가한다(벡터 채널에 섞으면 주제가 흐려진다).

### C1. 검색 품질 평가

| 항목 | 원안 | 대체 |
|---|---|---|
| 역생성 질의 | LLM이 데이터셋 설명에서 질의 생성 | **사람이 작성하는 시나리오 질의 비중 확대** + 제목·키워드 기반 템플릿 준자동 생성 후 사람 검수 |
| 관련성 라벨링 | LLM-as-judge 초안 + 사람 검수 | **전량 사람 라벨** (질의 40개 × 평균 15건 ≈ 600건, 2명 반나절) |

> 💡 **이 제약이 오히려 유리한 면이 있다.** LLM-as-judge는 어휘 누출 편향·자기선호 편향·
> 재현성 부재 때문에 "LLM 라벨만으로 결론 내지 말고 사람 라벨과의 일치도(κ)를 함께 보고하라"는
> 단서가 항상 따라붙는다. 전량 사람 라벨이면 그 논란 자체가 없어져 **평가 근거가 더 강해진다.**

### C7. 외부 모듈 연계

과업 문구의 요점은 "외부 모듈을 **교체 가능하게 연계**한다"이지 "상용 API를 쓴다"가 아니다.
→ **어댑터 규약은 OpenAI 호환 `/v1/chat/completions`를 그대로 유지**하고,
구현체만 로컬 `llama-server`를 가리킨다. 정책이 바뀌면 `LLM_BASE_URL` 교체로 끝난다.
**이 구조 자체가 과업 요구(교체 가능성)의 증거가 된다.**

### 이미지 (A2 부속)

VLM 캡셔닝은 GPU 없이는 1건당 수십 초~수 분이라 포기한다.
대체: 이미지 기본 메타(해상도·종횡비·대표색·pHash) → 🟦 CLIP zero-shot 태깅
(생성이 아니라 **분류**이므로 CPU로 감당 가능). ⚠️ EXIF GPS는 개인정보 위험으로 제거한다.

## 로컬 sLLM 운영 제약

- **CPU 상한은 사실상 4B급 Q4 양자화까지.** 7~8B는 노후·저코어 CPU에서 요약 1건당 30초~1분이라
  수만 건 배치가 비현실적이다.
- 요약 1건 ≈ 5~15초 가정 시 10,000건 ≈ **14~42시간(단일 워커)** → 야간 CronJob + 복수 Pod 수평 분할.
- **입력 절삭**(앞 N토큰 + 구조 기반 발췌)이 가장 효과 큰 비용 절감 수단이다.
- 동시성은 **세마포어로 1~2건 고정** — CPU 추론은 동시 요청이 늘면 전체가 느려진다.
- ⚠️ 인용 수치는 2차 자료 기반이다. **실제 노드에서 `llama-bench` 측정 후** Pod 수·배치 크기를 확정한다.

## 과제 문서 서술 시 주의

**"비동기 배치 생성"으로 명시하고, 실시간 LLM 응답을 약속하지 않는다.**

## 전제 — 확인 완료 (2026-10-27)

**"외부 API는 불가하나 온프레미스 로컬 추론은 가능"** 이 확인되었다.
따라서 A2 목표선(로컬 sLLM 생성 요약)은 **실현 가능한 계획**으로 유지한다.

다만 **최소선은 여전히 LLM 없이 성립하도록 유지한다.** 이유는 두 가지다.

1. 로컬 sLLM은 `llama-bench` 실측 전까지 처리량이 확정되지 않는다.
   수만 건 배치가 현실적이지 않은 것으로 나오면 적용 범위를 좁혀야 한다.
2. 모델·런타임 장애 시에도 메타데이터 생성 파이프라인이 멈추지 않아야 한다.

구동 설계는 development/04_Implementation_Methods.md §3 C7 참조.
